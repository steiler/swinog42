How we configure them today

  • One-shot: the pipeline pushes once and moves on
  • Slow iterations: every change goes through the pipeline
  • No monitoring: nobody watches the result

Where we are today: a pipeline (Jenkins) triggers Ansible, Ansible reads the configuration from git and pushes it to each CNF. KRM in three beats, left to right: a CRD extends the Kubernetes API with a new kind; a CR is an instance of that kind (just YAML, applied like any other object); an operator or controller adds the business logic that watches the resource and acts on it. The point for this talk: once something is a resource, it gets kubectl, RBAC, GitOps and the control loop for free. Next: that is exactly what we want for network function configuration. Example names (Config, upf-config) are illustrative; the SDC part later uses the real kind (Config, config.sdcio.dev).

The control loop is the heart of Kubernetes: watch for changes, perform an action, update resources, repeat. Built-in controllers (Deployment, Job, PersistentVolume) work like this, and so do third-party operators (Prometheus Operator, External Secrets Operator, cert-manager). Diagram: the user only talks to the Kube API; the API stores custom and built-in resources; the operator reads/writes through the API and receives events when something changes. That is the pattern we want for network function configuration.

Three protocols, three transports, several encodings: this is what makes network configuration look messy from the outside. What they share is the YANG schema underneath. Because the schema describes the data, a tool can convert between encodings and validate a configuration regardless of the protocol used to deliver it. That is why SDC can speak NETCONF and gNMI without vendor-specific code. RESTCONF is greyed out on purpose: SDC does not support it today (the protocol is a pluggable driver, so it is a possible addition, not a promise). Say that out loud if somebody asks.

YANG – Network Function Schema

Schema (YANG)
list device {
  key "name";
  leaf name { type string; }
  leaf role {
    type enumeration { enum spine; enum leaf; }
    mandatory true;
  }
  leaf mgmt-ip {
    type inet:ipv4-address;
    must "starts-with(., '10.')" {
      error-message "IP must be 10.x.x.x";
    }
  }
}
→
Configuration (XML)
<device>
  <name>leaf-1</name>
  <role>leaf</role>
  <mgmt-ip>10.1.1.10</mgmt-ip>
</device>
<device>
  <name>spine-1</name>
  <role>spine</role>
  <mgmt-ip>10.2.0.1</mgmt-ip>
</device>
✓ accepted
mgmt-ip 10.1.1.10
✗ rejected
mgmt-ip 192.168.1.1: IP must be 10.x.x.x
✗ rejected
role router: not one of spine, leaf
Left: the schema, a model of what a valid configuration looks like: a list of devices, a mandatory role from an enumeration, and a management IP that must be an IPv4 address in 10.x.x.x. Right: configuration data that conforms to it (shown as XML, the same data could be JSON). Bottom: the point of a schema: a value that violates it is rejected with a clear error before it ever reaches the device. This is the "validate" step of the wish list. The schema is a simplified, illustrative example.

An intent's journey to the device

High-level gain: SDC does not forward your Config. It builds ONE tree per device from three inputs (all intents with their priorities, the device's running config incl. brownfield, the YANG model), validates the WHOLE result, and pushes only the difference to the device. This slide comes right after the Config slide — before Intent resolution: recap, do not re-teach priority yet (about 60-90 s). Walk the diagram only: parallel inputs into 1 Merge, 2 Validate, then 3 Diff (what changed versus the device) and 4 Translate (turn the delta into the southbound format). Diff and translate are separate on purpose: the tree is complete before anything is computed or sent. Read-back loop sets up Deviations. No bottom bullets; detail stays in notes. Docs (system-architecture/data-server): candidate tree = deep copy of the synced (running) tree + all intents; same leaf set by several intents: lowest priority NUMBER wins; YANG validation; diff; only then the south-bound Set (confirmed commit with auto-rollback timer). Brownfield: stays in the tree as 'running' with the lowest precedence. No intent owns it, so it is reported as an UNHANDLED deviation; SDC does not remove it. Rollback: the push is a confirmed commit. If the transaction is not confirmed within the timeout, data-server re-runs the previous intent content and the device returns to its prior state. Rejection (say it out loud): a config that fails validation never reaches the device, and the user sees the error on the Config. Discovery (one sentence): a DiscoveryRule finds the device and creates its Target, so you never write one. Translate (one sentence, optional): after diff, only the delta is encoded for NETCONF or gNMI. Roadmap (do not dwell): a further per-NOS layer will shape how updates are packaged, e.g. one gNMI Set per YANG module with JSON-IETF where the OS requires it instead of one bulk update under /. That is why translate stays its own step, not folded into diff. Kubernetes speaks resources; the device speaks YANG over the driver. No per-vendor CRDs in your cluster. Read-back (sync): subscriptions/polling keep the tree current; mismatch between winner and device = deviation. Backup slide after this one shows the real pods, only open it if asked.

The lower the priority number, the higher the precedence.

Without competition, the result is simply a merge of all intents.

Delete overlap-config: back to 192.0.2.10, nothing was lost.

After the journey diagram: a story, not an abstraction: three owners with different roles; priority expresses who is allowed to win. Rule: lower number = higher precedence (docs: priority is a tie-breaker when Configs overlap). Say it out loud. Build order: 1. the platform team's baseline (prio 100) sets eth0 ipv4-address 192.0.2.10 and mtu 9000. 2. Ops put a temporary override with prio 50: it sets the SAME leaf ipv4-address (20.20.20.20, wins because 50 beats 100) and a NEW leaf description (uplink). 3. Merged result: ipv4-address from the override, mtu from the baseline, description from the override: different leaves never compete, they are simply merged. 4. Delete the override: ipv4-address falls back to 192.0.2.10 and description goes away: the lower-priority intent was never lost. The best demo of why this matters is the last bullet: the lower-priority intent is still stored, so removing the override restores it automatically. (With deletionPolicy delete, removing overlap-config also removes its values from the device; the baseline value then takes over.) Paths are xpath notation, the same as 'runningconfig --format xpath', the deviation slide and the blame tree (root node 'network' in this example model; use your real model's paths). A Config sets LEAVES: the full path to the leaf is what identifies it, and two Configs conflict only when they set the SAME leaf (here ipv4-address of eth0). Setting different leaves, even under the same list entry, just merges. Same Configs as in the blame slide (initial-config, new-interface, overlap-config) so the audience recognises them. Role names and priorities are made up for the story: adapt to what the Swisscom case really looks like (e.g. vendor baseline vs. site-specific vs. temporary change). Title ties back to the Config slide ("what if it drifts"): drift = running config no longer matches intent; SDC records it as a Deviation with a reason. Point at metadata.name device01-baseconfig: one Deviation per device per intent — same pairing as a rolled-out Config (device + intent in the name). Concrete example for each reason: - NOT_APPLIED: someone changed svc-a bandwidth on the device to 100. - OVERRULED: eth0 ipv4 from new-interface vs overlap-config (previous slide). - UNHANDLED: a loopback someone configured by hand. What SDC does (verified in docs): - NOT_APPLIED: always reported (same column as OVERRULED/UNHANDLED). Non-revertive: SDC does not re-push; accept drift with kubectl sdc deviation --revert, or change the Config. - NOT_APPLIED + revertive: exception on the slide sub-line — SDC re-applies the Config and the deviation goes away ("self-healing"). - OVERRULED: reported only; SDC never changes the overriding config. - UNHANDLED: reported only; with no Config CR all brownfield config is one UNHANDLED deviation per target. SDC creates one Deviation per Target and one per Config CR.

What blame IS: a single view that combines the RUNNING config (what is on the device), the INTENDED config (what the Configs want) and the DEVIATIONS (where they differ), as a tree, and tags each leaf with the source of the highest-precedence value (a Config, 'default', or 'running' if no Config owns it). So it answers three questions at once: what is on the device, who put it there, and does it match the intent. That is why a deviated leaf shows 'actual [~> expected]' and a (*) next to its owner. It also shows the other half of the priority story: the OVERRULED leaf (eth0 ipv4) is attributed to the winning Config. The output is a TREE (the config is a tree, blame shows it as one) with the owner in a left column, same layout as the kubectl-sdc README (default format 'tree'; --format xpath gives one line per leaf).
